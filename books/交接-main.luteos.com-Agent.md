## 三、你要做什么

### 阶段 1 · 检查（只读，先别改）

1. 拉最新 `main`，确认 `a4acc4d` 存在。
2. 跑 `node scripts/site/build.mjs`，确认：
   - 无孤儿文件报错
   - 30 页正常生成
3. 本地打开 `docs/site/design.html`、`build.html`、`verify.html`，检查：
   - 案例区块位置是否正确（在「谁来验」之后）
   - 页内导航是否出现「真实案例」
   - 表格在 390px 窄屏下是否溢出
   - 是否与「实战避坑守则」内容重复
   - 案例文案是否偏离 ANB 的读者定位（**不写代码的产品开发者**）

**产出**：一份检查清单，逐项标注"通过 / 需调整"。

### 阶段 2 · 融合（按检查结果调整）

可能的调整方向（**只改必要的，别扩大**）：

| 方向 | 判断依据 |
|---|---|
| **文案产品化** | 案例里的工程术语（"迁移脚本""部署门"）是否该换成产品语言？ |
| **位置** | 案例是否该放在分支卡片旁边，而不是「谁来验」之后？ |
| **数量** | 8 个是否太多？verify 的 5 个是否该合并成 3 个？ |
| **补"怎么用"** | 每个案例是否需要加一句"你遇到时可以怎么做"？ |

**原则**：案例是**新增**，不替换 ANB 原有内容。原有一字不改。

### 阶段 3 · 优化

| 项 | 做什么 |
|---|---|
| 移动端 | 三列表格在窄屏可能太挤 → 考虑改成卡片 |
| 锚点 | 给每条案例加 `id`，方便从分支表跳转 |
| 去重 | 检查是否与「实战避坑守则」重复，重复的删一边 |
| 数据标注 | 确认"来自 2,794 个工程实现会话"这句准确，且不误导 |

### 阶段 4 · 部署

**部署前确认**（这是生产操作）：

1. 部署会**重启共享 nginx 网关**（`ai_video_nginx`），影响服务器上其他 30+ 站点。
2. 按项目规矩，这属于**必须逐次获得人类确认**的动作。

**部署步骤**：

```bash
# 本地构建镜像 + 打包
bash deploy/pack-context.sh

# 部署到服务器（会重启共享网关）
bash deploy/deploy-release.sh
```

**部署后验证**：

```bash
curl -sI https://main.luteos.com/verify.html | head -3
curl -s https://main.luteos.com/verify.html | grep -c 'id="cases"'
```
