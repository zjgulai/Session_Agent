## 设计（2 条）

### 交接契约只写了"它做什么"

**ANB 原文**：每个工具三行，第二行「什么时候别用」是重点，也是最常被省掉的。

**会话案例**：

> 权限文档测试失败：新增了 `cloud` 权限说明，但测试里的"已审查 flags 列表"还没登记。补上 `cloud: ["no local CLI"]` 后重跑。

**说明**：契约新增了一项权限，但**下游的登记表没同步**——"它做什么"写了，"它和谁有关、什么时候别用"没写。

### 输入存在，但散在好几处

**ANB 原文**：拒绝清单要对照的政策，散在好几处——既不是"有"，也不是"没有"，中间那件"拢成一份"的工作没人负责。

**会话案例**：

> README/TODO 说明数据采集侧仍保留早期额度阻断记录，但 README 已注明后续已完成补采。需要区分"已实现能力"和"文档陈旧项"。

**说明**：同一事实分散在 README、TODO、代码三处，且互相矛盾。**"拢成一份"的工作确实没人负责。**

## 开发（1 条）

### 结果来自样例数据

**ANB 原文**：跑通了，但结果来自样例/固定数据。

**会话案例**：

> 隔离假数据测试 **64 项通过**；浏览器测试只完成收集，**未运行**。未启动 Web 或 Worker，未读取真实案例。

**说明**：64 项全绿，但全是假数据；真实验证一项没做。**"全绿"和"能用"之间隔着一整个真实数据层。**

> 参考实现的使用边界也必须写进方案：它是开放参考代码，**示例数据是虚构的**，官方明确表示它不是受支持产品、没有 SLA，也不负责生产部署中的认证、权限、业务规则和合规。

**说明**：连参考实现自己都声明"示例数据是虚构的"——**用它的数据跑通，证明不了任何事**。

## 验收（4 条，材料最足）

### 一条检查都没有

**ANB 原文**：先写五到十条判断标准，再改产品。

**会话案例**：

> 工程质量门禁很薄：**build 不是 typecheck，CI 只跑 JSON 验证**，仓库**没有测试/视觉回归/可访问性检查**。

**说明**：有 CI，但只验证 JSON 语法。这就是"一条真正的检查都没有"。

### 检查从没红过

**ANB 原文**：一条从没失败过的检查，只有三种可能：没在跑、没接进判定、写得太松。

**会话案例**：

> 回归断言已加；现在运行这一个 e2e 用例，**确认它会在现有模板下失败，避免测试只是空转**。

**说明**：主动去"证明检查会红"——这正是 ANB 说的"故意弄坏"。

### 检查红了

**ANB 原文**：先别让它修。先问：是产品错了还是尺子错？

**会话案例**：

> **RED 阶段符合预期**：测试失败，因为目标脚本不存在，第二个用例明确报 `MODULE_NOT_FOUND`。

**说明**：先确认"红得对"（因为脚本不存在），再去实现。**没有直接改代码迁就测试。**

> 三条红的，三条全是测试自己写错：我把字符数算错、把排序预期写反。

**说明**：这是 ANB 原文提到的同一个实测——**红的可能是尺子错**。

### 全绿但结果不好

**ANB 原文**：机制可信 ≠ 产出可用。

**会话案例**：

> 本地 E2E 通过，**不等于线上逐页视觉巡检**。

> 把公网验收脚本的"假绿"补掉：它以后**不仅检查首页标题，还会抓取实际 JavaScript 资产并验证数据版本标记**。这样**旧页面即使仍返回 200，也不能冒充新版本上线成功**。

**说明**：这是最精彩的一条——**200 是"机制可信"，"新版本真的上线了"才是"产出可用"**。两者之间差一个资产版本校验。

### 补充：检查写得太松（ANB 未单列，但案例极多）

这是"检查从没红过"最常见的成因：

| 案例 | 松在哪 |
|---|---|
| `migrate` 只验证 active ID 是否存在，**不检查项目是否已归档** | 只查存在，不查状态 |
| 部署门**仅检查 root 非空、不是 `/` 且目录存在**，没有验证 canonical path、owner、mode 或项目 sentinel | 只查形式，不查语义 |
| 两个 CSV **只检查存在，不解析、不对账** | 只查文件在不在 |
| gate **只检查编号、存在性和数量**，不检查摘要、状态、链接是否语义正确 | 只查结构，不查内容 |
| gate **只检查路径存在，不验证 Markdown anchor 是否存在** | 只查路径，不查锚点 |

**统一模式**：`只检查 X 存在，不检查 X 正确`。

## 管理（2 条）

### 文档数字与实际不符

**ANB 原文**：文档里的数字和实际对不上。

**会话案例**（这类最多）：

| 文档说 | 实际是 |
|---|---|
| README 写 **8 个 agents** | 代码已注册 **17 个** |
| README 写 Metrics 是 **10 个指标** | `audit.json` 已是 **11 个** |
| 文档写"**16 个按需**" | 当前真实状态不同 |
| 私有 README 残留**旧命名说明** | 实际文件已是 `dept-*--*.md` |
| README 写最后 session 是 **2026-06-17** | 仓库已有 **2026-07-29.json** |

**共性**：文档是**手写的快照**，代码是**活的**。两者必然漂移。

**解法**（会话里也有）：统计从文件系统**自动重建**，文档只做呈现。

### 状态记不清

**ANB 原文**：你记不清它现在是什么状态。

**会话案例**：

> `PROGRESS.md` 混合历史记录和当前路线图。

> 先读取现有 `CURRENT_STATE.md`，确认当前状态，避免和已有状态冲突。

**说明**：状态文档混了"历史"和"当前"，导致**读的人无法判断哪条是现在有效的**。

## 交付 / 运营 / 迭代（0 条）

这三类的误判（只有你能打开、别人一进来就撞墙、没人告诉你哪不好、不知道跑了多少次、总数对不上、不知道有没有人用、要加新功能、想抽通用模板、想保留说不清理由）**在会话里没有可靠对应**。

**原因**：
- 交付：你的交付通常是内部系统，没有"陌生人首次使用"的场景
- 运营：几乎没有上线后的使用数据
- 迭代：项目周期短，还没到"抽模板/删功能"的阶段

**建议**：保持 ANB 原文，标注"本节未用会话验证"。

## 删除记录（诚实标注）

初版有 4 条案例，经复核删掉：

| 删除的案例 | 为什么删 |
|---|---|
| 运营「总数与分项对不上」→ `records=13 errors=0 ledger_total=0` | 这是**正常的对账输出**，不是"对不上"。误读了上下文 |
| 交付「没人告诉你哪不好」→ `手册无 Before State` | 这讲的是**内容质量**，不是**缺反馈机制**。两者不是一回事 |
| 开发「只对一种输入有效」→ `migrate 只检查 active ID` | 这其实是「检查太松」，不是「输入覆盖窄」。归错了类 |
| 迭代「想抽通用模板」→ `先跑第二个项目验证可复用性` | 这是「验证方法」，不是「误判本身」。牵强 |

**原则**：宁可少，不可掺沙。
