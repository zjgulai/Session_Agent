> 状态：**调研完成，待你确认方案后执行**。

## 一、ANB 是什么

**Agent Native Builder**：一套给**不写代码的产品开发者**用的 agent 产品方法论。

**核心目标**：
> 让你能判断自己做的东西是**真的能用**，还是**只是看起来能用**。

**结构**：
- **七阶段**：需求 → 设计 → 开发 → 验收 → 交付 → 运营 → 迭代（+ 管理）
- **每阶段 8 板块**：走哪条路 / 误判 / 通过标准 / 谁验 / 避坑守则 / 实战用法 / 用到哪些 skill / 原文
- **分支总表**：46 条判断，**按代价排序**
- **Skill 全表**：177 个，每个标"它坏了会怎样"
- **8+3 层契约** · 13 张数据表样张 · 2 份实测报告

## 二、核心发现：目标读者错位

这是本次调研最重要的结论。

| 信号 | 会话占比 |
|---|---:|
| **工程实现语言**（实现/重构/测试/部署/接口/数据库/架构） | **92%** |
| 产品设计语言 | 9% |
| 不写代码 / 不会写 | **2%** |
| 提需求给别人做 | **0%** |

**ANB 写给"不写代码的产品开发者"；你的会话是"工程实现者"。**

### 这意味着什么

| ANB 阶段 | 会话材料 | 原因 |
|---|---:|---|
| **验收 verify** | **86%** | 🟢 主战场，材料极丰富 |
| **设计 design** | **83%** | 🟢 主战场 |
| 开发 build | 64% | 🟢 丰富 |
| 管理 manage | 59% | 🟢 丰富 |
| 交付 ship | 57% | 🟢 丰富 |
| 迭代 iterate | 25% | 🟡 中等 |
| **需求 need** | **24%** | 🔴 你不做"功能清单/品类"式需求 |
| **运营 operate** | **19%** | 🔴 几乎没有运营数据 |

**结论**：
- **重叠区**（设计/开发/验收/交付/管理）：可大量补充
- **不重叠区**（需求/运营）：材料稀少，不宜硬凑

## 三、可蒸馏的三个方向（A / B / C）

### A · 为误判配真实案例

ANB 有 28 条误判，但**大多没有具体案例**。会话里有真实记录。

**已验证可配案例的误判**：

| ANB 误判 | 会话里的真实案例（抽象） |
|---|---|
| **结果来自样例数据** | `示例数据是虚构的，Anthropic 明确表示它不是受支持产品`<br>`隔离假数据测试 64 项通过；浏览器测试只完成收集，未运行` |
| **总数与分项对不上** | `candidate-ranking.csv 与 rejected-sessions.csv 只检查存在，不解析、不对账` |
| **文档数字与实际不符** | `README 仍写 8 个 agents，但代码已注册 17 个`<br>`README 仍把最后 session 写为 2026-06-17，但仓库已有 2026-07-29.json` |
| **检查从没红过** | `避免测试只是空转` |
| **检查红了** | `RED 阶段符合预期：测试失败，因为目标脚本不存在` |
| **一条检查都没有** | `没有测试/视觉回归/可访问性检查；CI 只跑 JSON 验证` |
| **全绿但结果不好** | `本地 E2E 通过，不等于线上逐页视觉巡检` |

**无法配案例的误判**（不重叠区）：
- 功能清单不是问题
- 品类不是用途
- 拒绝清单写成价值观
- 权限按重要性排错

→ 这些是"产品开发者"的误判，你的会话里没有。

### B · 为分支加实证频率

**重要限制**：我试过给全部 46 条分支做关键词统计，结果**大部分不可信**。

| 分支 | 关键词统计 | 抽样验证 | 判定 |
|---|---:|---|---|
| b-fake（样例数据） | 35% | `fixture`/`mock` 是正常测试做法 | ❌ **假阳性** |
| b-local（只有你能打开） | 25% | `localhost` 是正常开发验证 | ❌ **假阳性** |
| b-red（检查红了） | 3% | `RED 阶段符合预期` | ✅ 可信 |
| b-none（没有检查） | 2% | `没有测试/视觉回归` | ✅ 可信 |
| b-reconcile（总数对不上） | 5% | `只检查存在，不解析、不对账` | ✅ 可信 |

**结论**：只对**语义明确**的分支报频率，其余标"无法可靠统计"。

**可报的分支**（高置信）：b-red · b-none · b-reconcile · b-docdrift（文档数字漂移）

### C · 补充 ANB 没有的维度

这些在我已有的手册里，可直接映射：

| 我的产出 | ANB 缺什么 | 可放哪 |
|---|---|---|
| **卡 19 状态继承** | ANB 没讲"重跑时保留人工判断" | 管理阶段 |
| **卡 18 边界指令** | ANB 讲"怎么验"，没讲"怎么派活" | 需求/管理 |

| **方法演进史** | ANB 是静态方法论，缺"方法怎么变" | 元层 |

## 六、需要你确认的三点

1. **"不重叠区"怎么处理？**
   - (a) 明确标注"你的会话不覆盖，保持 ANB 原文"
   - (b) 用其他项目的会话补
   - (c) 跳过

2. **案例的抽象程度？**
   - (a) 保留具体技术细节（如 `README 写 8 个但实际 17 个`）
   - (b) 只保留模式（如"文档数字与实现漂移"）

3. **C 方向的映射粒度？**
   - (a) 每个维度单独成节
   - (b) 融进对应阶段的"补充"里

## 七、已知限制

| 限制 | 说明 |
|---|---|
| 目标读者错位 | 需求/运营阶段材料稀少 |
| 关键词统计不可靠 | 大部分分支无法量化 |
| 案例需人工筛选 | 正则只能定位，不能判断语义 |
| 未读 ANB 原文 HTML | 只读了渲染后的文本，可能有遗漏 |
| 会话含业务信息 | 案例必须抽象化 |

## 八、一句话

> **ANB 教"不写代码的人怎么判断产品能不能用"；你的会话记录"工程实现者怎么把东西做出来"。**
> **两者在"验收/开发/管理"重叠，在"需求/运营"分离。**
> **补充应该集中在重叠区，不重叠区如实标注。**
