# 发现 · 上下文成本是超线性的

> 数据：opencode 1,176 个会话的 token 账本（含 input / output / cache）。
> 结论：**会话越长，每条消息的 token 成本越高，呈幂律增长（指数 ≈1.43）。**

---

## 一、总量：input 是 output 的 152 倍

| 指标 | 数值 |
|---|---:|
| 总 input tokens | **38.9 亿** |
| 总 output tokens | 2,560 万 |
| 总 reasoning tokens | 40 万 |
| 总 cache read | **60.1 亿** |
| **input : output** | **152 : 1** |

**读法**：绝大部分 token 花在**输入**（读上下文），不是输出（写答案）。

---

## 二、随会话长度超线性增长

| 消息数 | 每消息 token（中位） | 总 input（中位） |
|---|---:|---:|
| 1–9 | 8,614 | 39,336 |
| 10–49 | 14,832 | 276,969 |
| 50–199 | 14,847 | 1,326,598 |
| **200–499** | **78,219** | **21,100,412** |
| **500+** | **109,818** | **74,960,233** |

- 每消息 token 从 **8.6K → 110K（13 倍）**
- 总 input 从 **39K → 75M（1,900 倍）**

### 幂律拟合

```
total_input ≈ e^8.40 × messages^1.43
R² = 0.748
```

- 指数 **1.43**：比线性（1.0）快，但**不到平方（2.0）**
- 说明：存在上下文压缩/截断机制，但**压缩不足以抵消累积**

---

## 三、极端案例

| 会话 | 消息数 | 总 input |
|---|---:|---:|
| 思维模型（长会话） | 921 | **4.27 亿** |
| Agent_agents（续跑） | 504 | 2.02 亿 |
| ana_caijing（PRD） | 600 | 2.35 亿 |

**单个会话 4.27 亿 input tokens**——相当于把一本几十万字的书重读了几百遍。

---

## 四、缓存是主要缓解，但不改变结构

- 缓存/输入比：**中位 0.97**（几乎 1:1）
- 总 cache read（60.1 亿）> 总 input（38.9 亿）

**含义**：绝大部分输入是缓存命中，实际计费成本远低于 token 数。
但**token 处理量本身仍是成本**：上下文窗口占用、延迟、以及缓存未命中时的费用尖峰。

---

## 五、工程含义

### 1. "开新会话"不只是整理，是降本

500+ 消息的会话，总 input 是中位会话的 **1,900 倍**。
把长任务切成多个短会话（配合断点恢复），可以显著降低 token 消耗。

**这给卡 03（断点恢复）补上了成本理由**：断点续跑不是"更整洁"，是"更便宜"。

### 2. 上下文压缩要主动做

既然成本是超线性的，就不能任由上下文堆积。
- 定期摘要
- 把探索过程移出主线程（子代理）
- 只保留结论与证据指针

### 3. 输出不是成本大头

input : output = 152 : 1。
**优化"写得更少"节省有限；优化"读得更少"才是关键。**

## 六、局限（诚实标注）

| 局限 | 说明 |
|---|---|
| **单一数据源** | 只有 opencode 的账本，Codex 无对应字段 |
| **cost 为 0** | 数据库里 cost 字段全为 0，只能看 token 量，看不到真实费用 |
| **不是平方** | 实际指数 1.43，说明有压缩机制，不能简单说"平方增长" |
| **无对照** | 没有"短会话 vs 长会话完成同一任务"的对照实验 |
| **因果不明** | 是"长会话导致高成本"，还是"复杂任务本来就长"——无法区分 |
