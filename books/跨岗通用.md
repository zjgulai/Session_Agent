# 分册 · 跨岗通用

> 三张卡，三个身份都用得上。完整卡（含证据与复现门）见 `../cards/`。

## 01 · 只读审计协议

**问题类**：对一个已有系统做零风险现状评估。**复现率 83%。**

**收敛解**：把评估固化为一条只读协议——声明不写 → 声明范围 → 声明维度 → 声明证据要求 → 声明产物。

**SOP**
1. 声明只读姿态，列出禁止动作（不运行/不下载/不提交）。
2. **先加载规则与上下文**（项目规则、计划、记忆）。
3. 声明范围（分支/工作区/目录）与维度（架构/合同/测试/安全/UI）。
4. 声明证据要求（结论要带回查路径）。
5. 运行指定验证（测试/构建/lint）。
6. 声明产物形态（清单/结论/缺口/风险）。
7. 附加约束（涉私有素材或外部网络时必加）。

**指令形状**
```
我会先核对 {范围}，再沿 {维度} 逐项 {动作}，
并保持全程只读、{附加约束}；产出 {产物}。
```

**坑**：只在标题写"只读"、指令里没写 → 模型中途仍可能写入。审计与修改混在同一会话 → 证据被覆盖。

## 03 · 断点恢复协议

**问题类**：长任务中断后接着做，且不基于过期结论。**复现率 100%。**

**收敛解**：**先验证断点，再续跑。** 核心不是"接着做"，而是"先证明接着做的前提还成立"。

**SOP**
1. 设只读边界（先声明只读，不动 index/Git/语料）。
2. 定位断点（读记忆/计划/TODO/冻结快照）。
3. **验证断点仍成立**（用当前代码/测试，**不继承旧结论**）。
4. 冻结当前状态证据（分支、HEAD、index、脏文件、哈希）。
5. 交叉核对计划/契约 vs 实际实现。
6. 跑验证门建立真实基线。
7. 从验证过的点续跑最小未完成单元。
8. 带硬证据 + 非动作清单收口。

**指令形状**
```
从上一步的断点恢复继续执行。
```
模型侧核心句：`但先用 {当前代码/测试} 验证，不直接照旧结论执行。`

**坑**：照旧结论直接执行 → 基于过期状态做出错误改动。这是最大坑。

## 04 · 对抗性审查技法

> **这是技法，不是问题类。** 它不是你"去请求"的东西，是你在**别的评估类里使用**的东西。出现率 30%（在"能力图谱"类里 86%）。

**问题类**：项目"看起来没问题"，但需要主动找错。

**收敛解**：**专攻"看似通过但未证明"的环节**，并区分已证实与推断。

**SOP**
1. 只读建立真实基线（分支、工作区、规范、构建验证入口）。
2. 拆多线并行检查（代码/架构、产品体验、资料发布治理）。
3. **专攻"看似通过但未证明"的环节**（核心动作）。
4. 区分已证实问题 vs 推断（推断必须标注）。
5. 输出核心优化点，模糊方向先讨论再动手。
6. 保持只读边界。

**反直觉重述句式**（本类最鲜明的标记）
```
不是 {表面问题}，而是 {真正问题}。
```
例：`不是"少几个功能"，而是若干测试绿色并不代表能力真实存在。`

**坑**：顺向检查冒充对抗性审查 → 只能确认已知项，发现不了未知风险。把推断当结论 → 制造虚假问题。

## 三张卡的共同底座

- 都从**只读基线**开始。
- 都要求**证据可回查**。
- 都把**"看起来成立"与"已被证明"分开**。
- 都在**改动前设边界**。
