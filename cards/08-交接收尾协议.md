## 场景

一个阶段做完，要么交给下一个会话，要么交给同事，要么隔几天自己回来。没有交接，上下文会丢，会重复劳动。

## 问题

- 不提交 → 改动丢失或被误覆盖。
- 不写交接 → 下一个会话不知道做到哪、下一步是什么。
- 交接只写"做了什么" → 无法判断"还剩什么"。
- 提交不干净 → 混入无关改动。

## 解决方案（收敛解）

**收尾 = 核对 → 定向改 → 验证 → 提交 → 写 handoff。** 产物是**两个**：干净的提交 + 一份交接文档。

核心：**交接文档必须写"未完成"和"下一步"**，不只写"已完成"。

## SOP（每步带独立 support）

| 步 | 动作 | support | 触发 | 决策点 |
|---|---|---:|---|---|
| H1 | 核对必读文档、分支、未提交改动 | 状态 30/32 · 提交 31/32 | 总是 | 有他人改动 → 不覆盖 |
| H2 | 确认需补充的关联（README / 索引 / 链接） | README 12/32 · 文档 26/32 | 有文档面 | 缺关联 → 补上，不留断链 |
| H3 | 定向修改，只改必要 | — | 总是 | 顺手重构 → 停，不夹带 |
| H4 | 验证（跑检查/测试） | — | 总是 | 未验证 → 明说原因 |
| H5 | 原子提交 + push（**保留远端历史，绝不 force push**） | push 14/32 · 复现门 3/3 | 总是 | 远端有分叉 → 用 merge commit 保留历史 |
| H6 | 在**具体路径**写 handoff 文档，MECE 分节（可追踪编号） | handoff 15/32 · 复现门 4/4 | 总是 | 只写"已完成" → 不合格 |
| H7 | 自检文档（内部链接 / 必填字段 / 结构） | 复现门 3/6 | 有文档面 | 断链/缺字段 → 修好再交 |

## 指令形状

```
先做一次完整的提交，然后写一个 handoff 交接文件。
```

模型侧展开：

```
我会先按项目指引核对 {必读文档、main 分支、未提交改动}，
再确认 {README/索引} 应补充的关联，
完成定向修改后执行验证、commit 与 push。
这里会用收尾验证流程，确保推送的是本次核实过的完整状态。
最后写 handoff：{状态 / 已做 / 未做 / 下一步}。
```

**关键句**：`确保推送的是本次核实过的完整状态`。

收口模板（复现门补入）：

```
已完成 {阶段}。最终状态：branch: {分支} / local HEAD: {sha} / remote HEAD: {sha} / working tree: {clean}。
本次已完成：{清单}。本次验证：{检查项}。未完成 / 未推送：{非动作清单}。
```

## 条件变体

| 条件 | 变体 | 差别 |
|---|---|---|
| 推到新仓库 | **迁移型** | 先核对，再推，并补 README 关联 |
| 交给下一个会话 | **会话交接型** | handoff 侧重状态与断点 |
| 交给同事 | **人交接型** | handoff 侧重背景与决策理由 |
| 阶段收尾 | **里程碑型** | handoff 含验收结论与剩余清单 |

## 反例与坑

- 不提交 → 改动丢失。
- 交接只写"已完成" → 下一个会话不知道还剩什么。
- 提交夹带无关改动 → 无法审查，无法回滚。
- 推送未验证的状态 → 把问题固化进历史。
- **边界**：纯探索、无产物的会话，不需要交接。

## 案例（抽象）

- 阶段收尾：commit + push + handoff（状态/已做/未做/下一步）。
- 推到新仓库：核对 → 补 README 关联 → 验证 → push。
- 交接给下一会话：写清断点与未完成项，供恢复协议使用。
