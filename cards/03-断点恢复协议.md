# 经验卡 · 断点恢复协议

- **身份**：跨三岗
- **问题类**：长任务中断后，从上次停下的地方继续，且不重复劳动、不基于过期结论
- **support**：合并语义类 **118 会话**（全量 2,794；原严格类 79，合并同义措辞后 +49）
- **全量 support（合并类）**：**R2 验证断点 = 116/118（98%）** · R7 收口 86% · R6 续跑 85% · R3 冻结状态 83% · R1 定位断点 82% · R0 只读边界 76% · R5 验证门 69% · R4 交叉核对 68%
- **置信级**：**高**（最大口径下核心主张 98% 成立；见 `../05-support-全量.md`）
- **脚手架判定**：配置语料**未**规定断点恢复协议；用户请求模板是用户自撰 → 判为**涌现**
- **口径**：样本级

## 场景

长任务跨会话中断（上下文满、会话重启、隔天继续）。需要接着做，但不能重头来，也不能照着过期结论做。

## 问题

- 重头做 = 浪费，且可能推翻已完成的工作。
- 照旧结论做 = 上次的断点可能已经失效（代码变了、测试变了）。
- 不声明状态 = 无法判断"从哪继续、还剩什么"。

## 解决方案（收敛解）

**先验证断点，再续跑**：定位上次断点 → 用当前代码与测试**验证**它是否仍成立 → 从验证过的点续跑 → 带证据收口。

核心不是"接着做"，而是 **"先证明接着做的前提还成立"**。模型的原话逻辑是：把记忆里的断点当**第一候选**，但先用当前状态验证，不直接照旧结论执行。

## SOP（每步带独立 support）

| 步 | 动作 | support（复现样本） | 触发 | 决策点 |
|---|---|---:|---|---|
| R0 | **设只读边界**（先声明只读，不动 index/Git/语料） | ~9/20 | 恢复前必做 | 任务本身要写 → 边界改为"先冻结再写" |
| R1 | 定位断点：读记忆/计划/TODO/冻结快照，找出上次停在哪 | ~10/20 | 总是 | 多个候选断点 → 按最近性排序 |
| R2 | **验证断点仍成立**（用当前代码/测试，**不继承旧结论**） | **~12/20** | 总是 | 断点已失效 → 重新定位，不硬续 |
| R3 | 冻结当前状态证据：分支、HEAD、index、脏文件、哈希 | ~9/20 | 总是 | 有未提交改动 → 视为用户所有，不回滚 |
| R4 | **交叉核对**：计划/契约 vs 实际实现（读测试证明了什么） | ~6/20 | 有 spec/计划时 | 契约与实现不符 → 先报差异，不擅自改 |
| R5 | 跑验证门建立真实基线（测试/类型/lint/构建） | ~11/20 | 有可运行验证 | 工具/版本不匹配 → 先复现，再判缺陷 |
| R6 | 从验证过的点续跑**最小未完成单元** | 总是 | 总是 | 大任务 → 按可验证单元切 |
| R7 | 带硬证据 + **非动作清单**收口 | ~8/20 | 总是 | 未完成 → 标 BLOCKED 与原因 |

**R2 是协议的核心**，独立抽取确认它是最一致的行为，且**没有任何会话是"信任旧结论不复查"**。

## 指令形状

```
从上一步的断点恢复继续执行。
```

用户侧模板极简（这是它的价值：一句话触发整套协议）。模型侧的展开形状：

```
记忆里的断点集中在 {断点描述}。我会把它当作第一候选阻塞点，
但先用 {当前代码/测试} 验证，不直接照旧结论执行。
先核对 {分支/工作区/staged}，再从 {验证过的点} 续跑最小单元。
```

**关键约束**：`不直接照旧结论执行`。这一句是协议的核心，缺了它，恢复就退化成"照旧执行"。

## 条件变体

| 条件 | 变体 | 差别 |
|---|---|---|
| 单会话内被截断 | **轻量恢复** | 直接续跑，跳过记忆检索 |
| 跨会话/跨天 | **完整恢复** | 记忆检索 + 断点验证 + 状态声明 |
| 上次有未提交改动 | **保现场恢复** | 视为用户改动，不回滚，先记录为证据 |
| 上次结论已过期 | **重定位恢复** | 丢弃旧断点，按当前状态重新定位 |
| 有 worktree 并行 | **多线恢复** | 逐 worktree 恢复，各自验证 |

## 反例与坑

- **照旧结论直接执行** → 基于过期状态，做出错误改动。这是最大坑。
- 不声明状态就续跑 → 覆盖了用户未提交的改动。
- 断点不唯一时不排序 → 从错误的点续跑。
- 恢复后不做单元验证 → 错误累积到收口才发现。
- **边界**：任务本身是探索性的、无明确断点结构时，不适用本协议。

## 案例（抽象）

- 从记忆找到"最近断点集中在 X"，先验证 X 是否仍成立，再续跑。
- 恢复后先跑 RED 命中根因，再最小修复，最后验证全绿。
- 收口时清点 P0/P1/P2 剩余，给出 `FINAL PASS` 或 `BLOCKED`。

## 成本依据（2026-11-07 补充）

断点恢复不只是"更整洁"，是**更便宜**。

opencode 账本显示：会话的 token 成本随消息数**超线性增长**（幂律指数 ≈1.43，R²=0.748）。

| 消息数 | 每消息 token（中位） | 总 input（中位） |
|---|---:|---:|
| 1–9 | 8,614 | 39K |
| 50–199 | 14,847 | 1.3M |
| 500+ | **109,818** | **75M** |

500+ 消息的会话，总 input 是中位会话的 **1,900 倍**。把长任务切成多个短会话并做断点恢复，能显著降低上下文成本。

详见 `../books/上下文成本-发现.md`。

## 复现门（P2）

- **方法**：第二个模型（Sonnet）读同一批 20 会话（`_raw/sample-resume.md`），独立抽取。
- **结果**：**通过。**
- **步骤复现**：R1–R6 **6/6 全部复现 = 100% ≥ 70%**。
- **核心主张证实**：R2"先验证断点再续跑"被独立确认为**最一致的行为（~12/20）**，且**无一例信任旧结论不复查**。
- **增量**：独立抽取补入 R0（只读边界）、R4（计划 vs 实现交叉核对）、R7（非动作清单）；并补出条件分支（脏工作区→停下问、写码前确认门、工具不匹配→先复现、工具不可用→不擅自安装）。
- **修正**：样本**混合**（4 个任务簇：TDD 实现 / 安全评审 / 计划交付 / 断点发现），但**同一句用户模板下协议不变** → 说明该协议**与任务类型无关**，是通用恢复协议。另有 3 对重复会话（2=3、10=11、19=20），已按去重计数。
- **裁决**：PASS。置信级 中高。

## 条件分支（复现门补充）

| 条件 | 行为 |
|---|---|
| 工作区脏 / 归属不明 | 停下，把归属决策交回用户，不覆盖、不折叠进新提交 |
| 要进入写码 | 先要书面确认门，确认后才写 |
| 工具/版本不匹配 | 先在精确版本下复现，再判是否为代码缺陷 |
| 工具不可用且禁止安装 | 退回本地可复现的人工流程，不擅自安装 |
