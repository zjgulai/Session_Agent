# 经验卡 · 项目诊断 → 债务/脆弱点 → 方案

- **身份**：产品经理 / Agent 全栈（跨岗）
- **问题类**：接手一个已有项目，要摸清它的问题并给出可执行改进计划
- **support**：严格类 **12 会话**（全量 2,794）
- **全量 support**：D1 画像 / D2 排查验证 / D3 证据锚定 / D4 严重度清单 / D5 方案 = **均 100%** · D7 下一步 92% · D0 元声明 83% · D6 非破坏边界 83% · D5b 测试矩阵 75%
- **置信级**：中（严格类样本小 n=12，但步骤一致度极高；见 `../05-support-全量.md`）
- **脚手架判定**：配置语料要求"定义可验证完成标准""大修改扩大测试范围"，与本协议**部分重叠** → **半脚手架**：底层要求来自配置，"债务分类 + 严重度排序 + 分阶段"的组织方式是涌现
- **口径**：样本级；四段中"测试矩阵/验收"为最弱段，已降级

## 场景

接手或接手中的项目，需要判断它哪里会出事、哪里该先改，并给出能被批准的改进计划。

## 问题

- 一上来就改，会踩到看不见的坑。
- 只说"有风险"没用，没有严重度和优先级就无法决策。
- 没有验收标准的方案，无法判断改完没有。

## 解决方案（收敛解）

把"诊断"固化为一条**五段协议**：元声明 → 现状画像 → 分层排查与验证 → 严重度排序清单 → 分阶段方案（含验收）。

## SOP（每步带独立 support）

| 步 | 动作 | support（复现样本） | 触发 | 决策点 |
|---|---|---:|---|---|
| D0 | **开场元声明方法**（点名方法与工具/技能） | 19/20 | 总是 | 声明方法与实际动作须一致 |
| D1 | 建立现状画像：结构、入口、配置、依赖、测试 | ~20/20 | 总是 | 文档与实物矛盾 → 记录矛盾，以实物为准 |
| D2 | 分层排查 + **经验性验证**（跑脚本/测试/构建/探测） | 扫描 ~7/20 · 验证 ~11/20 | 存在可运行验证 | 区分"潜在风险"与"已证实缺陷" |
| D3 | **发现锚定到文件/行，并标证据级** | ~7/20 | 总是 | 无锚点 = 不可回查 |
| D4 | 产出问题清单，按严重度排序（P0/P1/P2） | ~13/20 | 总是 | 债务分类：技术债 / 工程债 / 文档债 / 管理债 |
| D5 | 分阶段方案 | ~14/20 | 总是 | 涉数据/权限 → 先写风险、回滚与验证方式 |
| D5b | 测试矩阵 + 验收标准 | **~10/20（纯类 ~3/7）** | 视项目成熟度 | **最弱段**：项目无测试时退化为"声明未验证及原因" |
| D6 | 声明非破坏性边界 | 13/20 | 审计型任务 | 与只读协议联动 |
| D7 | 结尾给下一步 / 门 / 交接 | ~15/20 | 总是 | 门未通过 → 明确标 BLOCKED |

## 指令形状

```
我会先 {侦察：结构/入口/配置/测试/依赖}，
再 {沿…逐层检查 / 多线并行}，
把 {发现} 按 {严重度} 排序，
然后产出 {分阶段方案} + {测试矩阵} + {验收标准}；
本轮只做 {非破坏性探索}，{不会改文件 / 不会提交}。
```

**固定短语**：`按风险排序` / `分阶段` / `测试矩阵` / `验收标准` / `只读` / `非破坏性`；
债务分类固定为 `脆弱点 / 风险点 / 技术债务 / 工程债务 / 项目管理债务 / 文档管理债务`。

## 条件变体

| 条件 | 变体 | 差别 |
|---|---|---|
| 有测试与 CI | **完整型** | 可跑现有测试定位失败信号 |
| 无测试、只有产物 | **侦察型** | 先判源码缺失与运行风险，方案含"补最小验证" |
| 生产环境 | **隔离型** | 先备份、dry run、迁移计划、回滚与数据核验 |
| 工作区有未提交改动 | **只读型** | 视为用户的改动，不回滚，记录为证据 |
| 用户要"诊断后修复" | **带修复型** | 只修低风险项，其余留待批准 |

## 反例与坑

- 不建画像直接列风险 → 清单是猜的，不可执行。
- 问题清单不分严重度 → 无法排优先级，等于没给。
- **测试矩阵/验收被高估**：纯类样本里只有约 3/7 真做到，多数只是"声明了要做"。→ 别把它当默认产出。
- 债务不分类型 → 技术债和管理债混在一起，责任人不明。
- **边界**：项目已有清晰架构与测试时，本协议退化为常规 feature 流程。

## 案例（抽象）

- 对静态站项目：判"只交付产物"还是"源码缺失"，给出 bundle 运行风险与最小验证方案。
- 对生产项目：先摸排技术债/工程债/文档债/管理债四类，再分阶段整合方案。
- 对 Agent 项目：结构画像 → 高风险模块 → 严重度清单 → 分阶段方案。
