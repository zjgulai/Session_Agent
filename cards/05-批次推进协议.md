- **身份**：Agent 全栈 / 产品经理
- **问题类**：用户批准后，安全地推进下一批工作，且不覆盖现场、不假装完成
- **support**：命中 69 会话；收敛模板 "同意下一步/下一批…开始执行" 复用 ~40
- **support**：合并语义类 **120 会话**（全量 2,794）
- **全量 support（合并类）**：B6 证据收口 98% · B3 验收闭环 97% · B5 提交卫生 94% · B1 预检 84% · B2 批次 78% · B2b RED 基线 50% · B7 BLOCKED 30% · **B4 独立审查 19%（条件性）**
- **置信级**：中高（见 `../05-support-全量.md`）
- **脚手架判定**：**高重叠**。`Gate`（16 配置文件）、`验收`（14）、`Batch`（11）、`independent`（36）、`改动已写入但未提交`（Codex AGENTS.md）均在配置语料中。
  **涌现部分**（不在配置）：`验收闭环` 15 · `预检回执` 12 · `核对结果` 12 · `机器可读矩阵` 8 · `六面闭合` 9

## 场景

用户说"同意，开始执行下一批"。此时任务从规划转入执行，风险从"想错"变成"做坏"。

## 问题

- 直接开干 → 可能覆盖前一批未提交的状态。
- 一次铺开全部 → 出错时无法定位，无法回滚。
- 自己给自己盖章 → 没有独立验收，假性通过。
- 收口含糊 → 无法判断"到底做完没有"。

## 解决方案（收敛解）

**批准 ≠ 直接执行。** 把它拆成：**预检 → 批次推进 → 每批验收闭环 → 带证据收口。**

核心是**批次粒度 + 每批闭环**：不一次铺开，每批必须收口才能开下一批。

## SOP（每步带独立 support）

| 步 | 动作 | support | 触发 | 决策点 |
|---|---|---:|---|---|
| B1 | **预检回执**：核分支、HEAD、工作区、前序阶段状态 | **6/6**（凡展示"开始工作"的会话） | 每次批准后 | 有前序未提交 → 先记录，不覆盖 |
| B2 | 按**批次**推进（Batch/Phase/revision 粒度），不一次铺开 | **20/20** | 总是 | 批太大 → 再切分 |
| B2b | **建 RED 基线**：先复现当前失败，再动手（TDD 红绿） | 复现门补入 | 有可运行验证 | 首个失败与预期不符 → 记录差异，不宣告通过 |
| B3 | 每批带**验收闭环**（跑指定验证：build/contract/E2E/a11y/lint） | 验收闭环 15 | 每批 | 无验收标准 → 先定义，再执行 |
| B4 | **独立审查门**：另一个 reviewer 角色复核，不自己盖章 | **全量 23/118 = 19%**（**条件性**：高影响批次才做） | 高影响批次 | 有 Important > 0 → **拒绝宣告完成**，请示是否继续修 |
| B5 | **提交卫生**：只暂存指定文件、单一提交、`diff --check`、staging 留空 | 5/20 | 有提交时 | staging 不空 → 不算收口 |
| B6 | 带证据收口：状态标签、HEAD、严重度计数、已落地、**非动作清单** | ~10/20 | 每批收口 | 有未做项 → 明写，不省略 |
| B7 | 未过门 → 标 BLOCKED，不假装推进 | 6/20 | 门未通过 | 阻塞 → 报阻塞与原因 |

## 指令形状

```
同意下一批建议，开始执行。
```

模型侧展开（预检）：

```
当前分支为 {分支} 且工作树{干净|脏}，{thread|前序阶段} 状态为 {状态}。
我的简短计划：先 {步骤1}，再 {步骤2}，最后 {验证 + 提交}。
```

模型侧收口模板（复现门补入，精确到字段）：

```
{批次} 已完成，状态 {Ready | DONE_WITH_CONCERNS | BLOCKED}。
已落地：{改动清单}。
验证：{检查项 + 计数}。
独立审查：Critical {n} / Important {n} / Minor {n}。
最终 HEAD {sha}，本批 {k} 个提交。staging 为空。
未做：{非动作清单}。
```

**状态词表**：`Ready` / `DONE_WITH_CONCERNS` / `CODE_READY_DB_VERIFICATION_BLOCKED` / `preflight-done`。

## 条件变体

| 条件 | 变体 | 差别 |
|---|---|---|
| 前序有未提交改动 | **保现场** | 先记录为证据，不覆盖、不折叠 |
| 多批可并行 | **worktree 并行** | 每批独立 worktree/分支 |
| 高风险批次 | **加独立门** | 必须独立复核才放行 |
| 门未过 | **BLOCKED** | 报阻塞与原因，不推进 |

## 反例与坑

- 批准后直接开干 → 覆盖前序状态。
- 一次铺开全部批次 → 出错无法定位。
- 自己盖章 → 假性通过。
- 收口只报"已完成" → 无法核验，等于没报。
- **本类最常见的证据升级**：`测试绿 ≠ 风险关闭`、`门未过 ≠ 可推进`（见 [卡 12 证据升级拒绝](12-证据升级拒绝.md)）。
- **边界**：单步小改、无批次结构时，本协议退化为直接执行。

## 案例（抽象）

- 多租户改造：按 Batch 推进，每批带独立终审，收口报 `0 Critical / 0 Important / 1 Minor`。
- 并行批次：每批开独立 worktree，收口后合并。
- 门未过：标 `Gate BLOCKED` + 下一门禁条件。
