# 经验卡 · 对抗性审查技法（跨类技法）

> **本卡是技法，不是问题类。**
> 它不是你"去请求"的东西，是你在**别的类里使用**的东西。初版把它当问题类，导致严格类只有 5–15 会话、置信级跌到"低"。语义分析纠正了这个归类错误。

- **类型**：跨类技法（嵌入在多个问题类中）
- **身份**：跨三岗
- **support**：技法出现在 **833/2,794 = 30%** 的会话中。分布：
  - **07 能力图谱 86%**（18/21）
  - 02 项目诊断 67%（8/12）
  - 04 对抗性审查（显式请求）44%（4/9）
  - 01 只读审计 31%（74/235）
- **置信级**：**中高**（技法高频且跨类稳定，复现门核心主张 14/20；"显式请求该技法"的会话稀有只是说明它是技法不是问题类，不影响技法本身的置信）
- **脚手架判定**：核心行为（找"看似通过但未证明"的环节、区分已证实/推断）**不在配置里** → 涌现
- **口径**：全量

## 场景

在**任何评估类任务**中（诊断、审计、能力盘点、评审），需要主动找错——不是为了否定，而是为了暴露"假性通过"。

## 问题

- 顺向检查只能确认"已知项没问题"，发现不了未知风险。
- 通过了的检查会掩盖"其实没验证"的环节。
- 直接问"哪里有问题"，模型会礼貌地答"整体良好"。

## 解决方案（收敛解）

**专攻"看似通过但未证明"的环节**，并**区分已证实与推断**。

核心不是"找 bug"，而是 **"找那些看起来通过、实际没被证明的环节"**。

## 技法（嵌入任意评估类）

| 步 | 动作 | 触发 | 决策点 |
|---|---|---|---|
| A1 | 只读建立真实基线 | 总是 | 基线不清 → 先冻结证据 |
| A2 | 拆多线并行检查（代码/架构、体验、发布治理） | 总是 | 线 ≥3 → 各线独立 |
| A3 | **专攻"看似通过但未证明"的环节** | 总是 | 这是核心动作，不可省 |
| A4 | **区分已证实问题 vs 推断** | 总是 | 推断必须标注，不得当结论 |
| A5 | 输出核心优化点，模糊方向先讨论 | 总是 | 方向模糊 → 先讨论再动手 |
| A6 | 只读边界 | 总是 | 审查与修复分离 |

## 指令形状

**显式请求**（稀有，~9 会话）：
```
对当前项目进行一次对抗性审查，识别核心优化点，
相关模糊的方向可以与我深度讨论 Grilling。
```

**嵌入用法**（高频，在任意评估类里）：
```
重点寻找"看似通过但未证明"的环节，
并把已证实问题与推断分开记录。
```

**关键句**：`重点寻找"看似通过但未证明"的环节`。缺了它，评估退化成普通 review。

## 反直觉重述句式

本技法最鲜明的标记：

```
不是 {表面问题}，而是 {真正问题}。
```

例：`不是"少几个功能"，而是若干测试绿色并不代表能力真实存在。`

## 证据分层（区分证实与推断的具体机制）

| 分层方式 | 例子 |
|---|---|
| 两级标签 | "潜在风险" vs "已证实缺陷" |
| 四态能力标签 | 代码证据 / 测试证据 / 阶段门证据 / 生产门证据，不混写 |
| 三层证据 | 页面宣称 / 可观察交互 / 可验证产出 |
| 五态安装区分 | 已安装 / 已启用 / 已连接 / 当前会话可调用 / 仅可搜索 |

## 条件变体

| 条件 | 变体 | 差别 |
|---|---|---|
| 有发布链/CI | **发布面优先** | 先查 CI/Pages，找"绿灯但没证明" |
| 有产品界面 | **体验闭环优先** | 验证"可理解→可操作→可复用"闭环 |
| 有图谱/知识库 | **反直觉优先** | 找"最密集域旁边的最大盲区" |
| 方向模糊 | **Grilling 变体** | 先与用户深挖方向，再审查 |

## 反例与坑

- 顺向检查冒充对抗性审查 → 只能确认已知项。
- 把推断当结论 → 制造虚假问题，浪费修复成本。
- 审查与修复混在一起 → 证据被覆盖，失去独立性。
- **边界**：项目处于探索期、无验收标准时，技法缺乏靶子。
