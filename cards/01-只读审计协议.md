# 经验卡 · 只读审计协议

- **身份**：跨三岗（Agent 全栈 / 产品经理 / 商业分析）
- **问题类**：对一个已有系统做零风险现状评估
- **support**：合并语义类 **235 会话**（全量 2,794）；只读声明 538 条（样本）
- **全量 support（合并类）**：S2 范围 98% · S3 维度 97% · S4 证据 97% · S1 只读 94% · S6 产物 94% · S5 运行验证 79% · S0 加载上下文 60% · S7 附加约束 16%（条件性）
- **置信级**：高（见 `../05-support-全量.md`）
- **脚手架判定**：配置语料只要求"写入前检查分支与工作区"，**未规定**"声明只读姿态"这一沟通协议 → 判为涌现（软复核通过）
- **口径**：样本级（Codex 200 / opencode 123），非全量；全量数字见 §证据指针

## 场景

需要评估一个已有系统：能不能发布、断点在哪、哪里该改。改动会覆盖现场，但结论必须可复核。

## 问题

- 直接改会破坏现场，且无法回滚。
- 只"看看"没有边界，结论不可复现。
- 范围不清，两次评估口径不同，无法决策。

## 解决方案（收敛解）

把评估固化为一条**只读协议**：声明不写 → 声明范围 → 声明维度 → 声明证据要求 → 声明产物。

## SOP（每步带独立 support）

顺序：**模式与约束 → 加载上下文 → 声明范围与维度 → 声明证据与验证 → 声明产物**。
（S0 与 S5 由 P2 复现门补入，见 §复现门。）

| 步 | 动作 | support | 触发 | 决策点 |
|---|---|---:|---|---|
| S1 | 声明只读姿态，列出禁止动作 | 94% | 任务属评估/审计/调研 | 用户已明确要改 → 跳过本协议 |
| **S0** | **先加载规则/上下文/记忆**（项目规则、计划、TODO、相关记忆） | 复现门补入 | 有 AGENTS.md / 记忆 / 前序计划 | 权威源有多个 → 先确认哪个为准 |
| S2 | 声明范围（分支/工作区/目录） | 63% | 总是 | 跨多模块 → 拆并行子任务 |
| S3 | 声明维度（架构/合同/测试/安全/UI） | 69% | 总是 | 维度 ≥3 → 每维度一条独立子任务 |
| S4 | 声明证据要求（回查路径） | 76% | 总是 | 无回查 = 口说，不可复核 |
| **S5** | **运行指定验证**（测试 / 构建 / lint / diff / HTTP 状态） | 复现门补入 | 存在可运行的验证 | 无测试 → 声明"未验证"及原因 |
| S6 | 声明产物形态（清单/结论/缺口/风险） | 40% | 总是 | 后续要改 → 产物含"最小修复方案"，但不实施 |
| S7 | 附加约束（不运行/不下载/不提交） | 同 S1 族 | 涉私有素材或外部网络时必加 | — |

## 指令形状

模型在 88% 的会话里收敛到同一个句式。抽象化后是全部步骤的最小载体：

```
我会先核对 {范围}，再沿 {维度} 逐项 {动作}，
并保持全程只读、{附加约束}；产出 {产物}。
```

**独立复现的第二版骨架**（来自 P2 门，更强调动作序列与依据）：

```
{我会 / 接下来我会} {按 <依据:项目规则 / 用户范围>} 做只读{任务类型}：
先 {动作1}，再 {动作2}，最后 {动作3}。{负向约束}。
```

两版的公共稳定部分是：**"先…再…最后…"的动作序列** 与 **结尾的负向约束句**。这两处是硬核，其余槽位可变。

**用法**：当模板填槽。缺槽 = 缺约束，模型会自行补，补的方向不可控。

## 条件变体

### 结构变体（按范围与目的）

| 条件 | 变体 | 差别 |
|---|---|---|
| 单模块、维度 ≤2 | **S 型** | 单线程，一条只读指令到底 |
| 跨模块、维度 ≥3 | **P 型** | 按维度拆独立只读子任务，各带回查产物 |
| 只读后要落地改动 | **A 型** | 产物含"最小修复方案"，不实施，另开会话实施 |

### 触发条件（P2 复现门补充）

| 条件 | 行为 |
|---|---|
| 用户给了 AGENTS.md / 项目规则 | 开场加"按项目规则"，并点名流程 |
| 涉及生产/线上/服务器 | 追加服务端约束（不推送、不 reload、不改权限），工作拆"本地 + 线上只读" |
| 前序阶段已完成 | 先报结果（"X 已通过"），再点下一步只读动作 |
| 存在阻塞/歧义 | 先提出阻塞问题，再继续 |
| 任务是 code review / 复核 | 承诺固定 review 格式输出 |
| 任务是实现/TDD | 先只读实现与测试风格，再写失败测试 |

## 审计 → 修复交接（A 型展开）

> **审计与修改分开之后，怎么接得上？** 这一节补的就是这条断链。
> 证据：审计产出清单的 1,021 会话中，**40%（408）** 含交接要素；其中验收 **79%**、优先级 **64%**、交接 56%、P0/P1 各 55%、执行计划 41%、回滚 25%、负责人 17%。

### 交接三件套

| 产物 | 内容 | 去向 |
|---|---|---|
| **① 审计报告** | 发现 + 每条证据（file:行号）+ 严重度 | 留存，供复核 |
| **② 修复计划** | 按优先级排序的任务清单，每条带验收标准 | 下一个会话的输入 |
| **③ 边界声明** | 本轮没改什么、没提交、没推送 | 防止误判"已修复" |

**核心**：审计的产物不是"一堆发现"，是**一份可被另一个会话直接执行的计划**。

### 计划必须带的字段

| 字段 | 为什么 |
|---|---|
| **优先级**（P0/P1/P2） | 不排序 = 无法决定先做哪个 |
| **验收标准** | 不写 = 改完不知道算不算完成 |
| **回滚方式** | 高风险项必备 |
| **负责人 / 下一会话** | 不指定 = 永远没人做 |
| **依赖** | 标出"必须先做 X 才能做 Y" |

### 交接格式

```
本轮只读审计完成，未修改任何文件、未提交、未推送。

发现（按严重度）：
- P0 {问题}：{file:行号} —— {影响}
- P1 {问题}：{file:行号} —— {影响}

修复计划（下一个会话执行）：
1. {任务}｜验收：{可观察结果}｜回滚：{方式}
2. {任务}｜验收：{可观察结果}｜回滚：{方式}

未做：{本轮明确没有做的事}
```

### 交接的三条纪律

1. **审计会话不修**——发现与修复分开，证据才不被覆盖。
2. **计划要能独立执行**——下一个会话只读计划，不应需要回读审计全文。
3. **明说"未修复"**——否则用户会以为审计即修复（卡 12 的 A ≠ B：`审计完成 ≠ 已修复`）。

### 反例

- 审计完只丢一堆发现，不转成计划 → 没人执行，等于白审。
- 计划没验收标准 → 修完无法判断是否完成。
- 在审计会话里顺手修 → 证据被覆盖，且无法区分"审计发现"与"修复改动"。
- 交接不说"未修复" → 用户误以为已经好了。

## 反例与坑

- 只在标题写"只读"，指令里没写 → 模型中途仍可能写入。
- 范围不给 → 扫描过宽、成本失控、结论稀释。
- 审计与修改混在同一会话 → 证据被覆盖。
- **边界**：探索性创作、明确要落地的实现任务，不适用本协议。

## 案例（抽象）

- 对内容站点做页面级可访问性审计：声明只读 + 按维度拆并行子任务 + 产出可回查问题清单。
- 对 Agent 项目做目录与路径依赖审计：只读盘点资产，输出缺口与风险。
- 对未提交实现做合同审计：只读核对接口契约，不改一行代码，给出最小修复方案。

## 复现门（P2）

- **方法**：第二个模型（Sonnet）读同一批 20 会话（`_raw/sample-readonly.md`），不知道本卡结论，独立抽取协议。
- **结果**：**5/6 步复现 = 83% ≥ 70% → 通过。**
- **增量**：独立抽取补入两步——③ 先加载规则/上下文/记忆；⑤ 运行指定验证。本卡已并入 S0 与 S5。
- **未通过项**：S2 声明范围 在独立抽取中只是隐含，未独立成步 → 记为弱项，待全量复核。
